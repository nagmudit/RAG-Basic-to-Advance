# Preface

This book is about one engineering question: **when a user asks a question, which evidence should enter the model's context, and why?** Retrieval-augmented generation (RAG) is treated here as a knowledge-access system rather than a single technique. Lexical search, structured queries, graph traversal, web retrieval, multimodal retrieval and dense vectors each have distinct roles, and each earns its place by solving a failure you can observe.

## Who this book is for

You can program at a basic level, but you may know no information retrieval, vector search, language-model internals or distributed systems. The path begins with a tiny searchable corpus and a hand-written search function. It ends with the ability to design, evaluate, secure and scale a multi-source retrieval platform.

By the end you should be able to build the key algorithms from scratch and trace a query through every stage. You should also be able to measure retrieval separately from answer quality, diagnose failures with evidence, and operate an instrumented service. The same goals include justifying architecture choices under latency, cost and permission constraints, and reading major research papers critically.

## How the book teaches

Every chapter starts from an observable problem. It introduces an intuitive model and says where that model stops being true, defines its terms, and traces data at index time and at query time. It derives only the mathematics the mechanism needs and works a small numerical example by hand. Then it implements the mechanism in a short Python program, and only after that looks at a production analogue. Alternatives are compared on quality, latency, cost, memory, freshness and operational complexity.

The order of topics follows a strict dependency graph. Postings come before BM25 and dynamic pruning. Vectors and similarity come before embeddings. Exact nearest-neighbour search comes before approximate search, and relevance labels come before ranking metrics. A full baseline RAG evaluation harness is built before any advanced architecture is attempted. A chapter may preview a later idea, but it never depends on one.

Claims are backed by experiments. Each experiment states its question, hypothesis, baseline, controls, frozen data, metrics and limitations. Negative results are kept, because a falsified hypothesis teaches as much as a gain. Figures are drawn from the same toy data as the prose, and plots are generated by programs you can rerun.

## How each chapter is organized

Each chapter opens with the question it answers and closes with a checklist that begins **"You understand this chapter if you can…"**. A hands-on lab follows the chapter. Attempt it before looking at the worked solutions{{solutions_note}}. Depth labels such as *Foundational*, *Intermediate*, *Advanced*, *Production* and *Research* mark how deep a topic goes, not who may read it.

## The running project

Across the book you evolve one system, **Build Your Own RAG Engine**. It starts with a handful of plain-text documents, explicit IDs, a hand-written search function and no model. Chapter by chapter it gains ranking, embeddings, indexing, ingestion, hybrid retrieval, reranking, context packing, generation, specialized sources, security and operations. Every upgrade begins with a failure case and keeps the previous version as a baseline, so each improvement is measured rather than assumed. Short, complete excerpts appear in the text. The full runnable code, fixtures and raw experiment records live in the book's source repository.
