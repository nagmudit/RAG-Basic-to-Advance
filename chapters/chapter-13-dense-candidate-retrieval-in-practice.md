# Chapter 13 — Dense candidate retrieval in practice [INTERMEDIATE]

Chapter 11 supplied a frozen encoder that sometimes retrieved paraphrases better than BM25. Chapter 12 showed that a tiny adaptation can reduce training loss without improving held-out retrieval. A prototype that recomputes passage embeddings in memory every run cannot yet answer operational questions: *which vectors correspond to this source snapshot; which model can query them; did a rebuild preserve ranking; where did time go; and which query classes still fail?* This chapter builds a **materialized exact dense candidate index** to make those questions testable. The same V0 corpus, V2 BM25 baseline, Chapter 9 judgments, Chapter 10 exact-vector oracle and Chapter 11 pinned model remain the prerequisites. The Chapter 12 adapter was rejected and is not silently deployed.

The practical rule is that the **embedding contract** is part of the index. It includes the source snapshot and segment IDs, precise indexed text, tokenizer/model revision, query and passage encoding roles, pooling, dimensionality, normalization, score metric, tie rule, and scope. A vector file without that contract is an uninterpretable collection of numbers. A high cosine score still produces only a *candidate*, not authorized, current or complete evidence. Read the [lab](../labs/chapter-13/LAB.md) after the mechanism; use the [separate solutions](../solutions/chapter-13-solutions.md) to check your trace.

## 1. Two paths with one representation contract

At **index time**, a source document becomes stable indexed segments in V1. V3 chooses `title + newline + indexed segment body` for each. The pinned shared sentence encoder maps each text to a 384-coordinate vector and L2-normalizes it. We store little-endian float32 coordinates in segment order, with a manifest that binds every row to its segment ID, allowed scope and searchable-text digest. The manifest also binds the exact model revision, masked-mean pooling, 256-word-piece limit, input format and vector-file checksum. Chapter 13's [snapshot builder](../projects/V3/dense_snapshot.py) writes all 13 V0 segments, including the legal-only teaching decoy, so the index can serve more than one trusted scope. It does **not** make D10 eligible for the support-team query path.

At **query time**, the same pinned encoder turns the user's question into a compatible normalized vector. A trusted eligibility decision defines which segment IDs may be scored; the local `support-team` string is a static fixture, not authentication. Exact cosine computes one score per eligible vector, then a deterministic top-*k* heap retains the highest results with ID ties. Only afterward can context construction choose excerpts. A later generator would see that selected evidence, not the whole search roster. Figure 13.01 traces the two lanes and the version gate.

**Figure 13.01 — Materialize once; validate on load, then score requests.** The startup manifest check prevents a query encoded with the wrong revision or text policy from using an old vector file. Eligibility precedes similarity; candidate ranking precedes context selection. The figure shows the Chapter 13 local path, not an ANN or service architecture.

The loader verifies the model ID and revision, corpus snapshot, every segment ID and searchable-text digest, scopes, dimension, float32 payload length and checksum, finite unit vectors, metric and tie rule. A wrong revision, changed title, missing row or corrupted byte fails closed. The binary file is deliberately simple so its bytes and identity are inspectable. A production index needs atomic publication, concurrent readers, update and deletion semantics, backups and a trusted authorization layer; those later dependencies are not implied by this local snapshot. A model revision must build a *new* index version before query traffic switches to it. Mixing 384-coordinate vectors from unrelated encoders is invalid even when the dimensions happen to match.

The pinned MiniLM checkpoint has no specialized query/document prompts, so this chapter preserves Chapter 11's shared `encode()` path. Other models may need distinct query and document prefixes or towers. [Sentence Transformers' official usage guide](https://www.sbert.net/docs/sentence_transformer/usage/usage.html) documents `encode_query()` and `encode_document()` and says they behave like ordinary encoding when no specialized prompts exist. Swapping to those calls without checking the model's prompt policy would change this experiment. A vector store does not repair incompatible representations.

## 2. Exact score, top-*k* and the cost of materialization

For normalized vectors `u` and `v`, cosine is their dot product: `cos(u,v)=u·v`, because both norms are one. The exact V3 scorer evaluates **all 12 eligible** support-team vectors before its heap chooses `k`. At dimension 384 that is `12×384=4,608` coordinate comparisons per query, plus selection work. The raw 13-row file is `13×384×4=19,968` bytes; its JSON manifest, source text, index objects and model weights are extra. At one million 384-dimensional float32 rows, raw coordinates alone require `1,536,000,000` bytes (about `1.43 GiB`). Exact scan work is `O(Nd)` and a size-*k* heap needs `O(k)` additional retained candidates; wall time depends heavily on memory layout, batching, implementation and hardware. Chapter 15 will examine when approximation is worth its recall loss, using this exact result as the geometric oracle.

Normalization is not cosmetic. For `q=(1,0)`, passage `a=(0.8,0.6)` has norm 1 and cosine `0.8`. Passage `b=(7,7)` has raw dot `7` but cosine `7/√98≈0.707`. Unnormalized dot ranks `b` above `a`; cosine ranks `a` above `b`. With normalized query and passage vectors, dot and cosine order agree, but the stored score scale still follows the declared metric. [Faiss's metric guide](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances) likewise distinguishes raw inner product from cosine and describes normalization for an inner-product index. Its [flat-index guide](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes) provides a production-library analogue; V3 uses its own inspectable exact scorer and does not introduce Faiss or ANN here.

The binary file keeps float32 vectors in row order. The manifest is the ID map; `row 7` alone is not a durable source locator. The loader validates every row before constructing the Chapter 10 `ExactIndex`. A query vector with a wrong dimension, a zero norm for cosine, or nonfinite values is rejected. The search enforces the support-team fixture **before** score calculation. Keeping D10 in the binary file but excluding it from candidate, context and timing work illustrates that permission is eligibility, never a low relevance score. Real services need policy updates and deletion propagation, which Chapters 21–22 will implement.

## 3. Batch build and request latency have different denominators

Index-time batching amortizes tokenizer/model overhead across passages. The [checked-in experiment](../projects/V3/chapter-13-experiment.json) warms the model, then times three passes over the **13 short texts** at batch sizes 1, 4 and 16. In this CPU run, median encode-only throughput is about `52.6`, `67.8` and `57.8` texts/second respectively. The largest requested batch is not fastest on this tiny fixture. `texts/second = 13 / (median milliseconds/1000)`; it is a throughput measurement for these texts and this hardware, not a promise about long documents or GPU batches. The fixed batch-size order can also confound thermal or cache effects. The separate snapshot build includes encoding plus serialization/checksum; loading the already built file includes validation and construction of the in-memory exact index. Model construction after imports and local cache access is recorded separately. None of those build costs belongs in the warmed request search time.

The Chapter 13 run also measures five warmed, randomized method-order samples per new diagnostic question. Its local p50 is about `0.090 ms` for BM25 **search only**. Dense query encoding is about `16.9 ms`, exact eligible scan and selection about `0.620 ms`, and their measured combined path about `17.5 ms`. The combined percentile is computed from combined request samples; it is not a sum of stage percentiles. These Python/CPU timings exclude context building and any generator, service network or cold process start. There are only 14 diagnostic questions, so the p95 sample is a teaching diagnostic rather than a production tail estimate. Batch indexing throughput and single-query request latency describe different workloads.

Every query trace should retain `query_id`, corpus/model/index versions, encoded-query contract, eligible count, scored-vector count, raw candidate IDs/scores, selected context IDs, latency by stage and a no-result or error reason. The checked-in V3 record has those local fields; it does not claim a distributed trace or authenticated identity. Raw source IDs and vectors may reveal sensitive information, so a real trace and derived-vector store must inherit source permission, licensing and retention rules. Counters by bounded slice and version are useful; raw questions or tenant IDs do not belong in low-cardinality metric labels.

## 4. Freeze ranking before diagnosing relevance

The first operational test is **parity**, not a new relevance claim. On the 17 Chapter 11 questions at `k=2` and `k=8`, the reloaded float32 snapshot and Chapter 11's in-memory exact index return the same ordered IDs in all `34/34` comparisons; the recorded raw-score difference is zero in this run. That confirms this materialization under the pinned encoder, source and machine. It does not prove relevance, nor would matching exact neighbors prove that an ANN index preserves qrel quality on a new workload.

The second test uses a new [14-question diagnostic qrel set](../projects/V3/judgments_ch13.json). One author reviewed all 12 eligible segments per question: `168` query–segment judgments. Two questions each probe acronyms, exact codes, negation, numeric constraints, colloquial language, exploratory Spanish-to-English retrieval, and no eligible evidence. Questions were fixed before model output. The Spanish probes are author-composed translations without independent native-language assessment; they cannot support a multilingual capability claim. The unchanged frozen dense index and unchanged V2 BM25 both search the same support-team roster at `k=2` and `k=8`.

## 5. Failure diagnosis by mechanism, not by model nickname

The current-target acronym probe asks for the Helios Pro Sev-1 **SLA**. The required direct segment is the signed amendment `D2:§2:0`; the old signed clause `D1:§3:0` is grade-1 historical context. BM25 ranks the FAQ and old clause; dense ranks the old clause and Basic-tier agreement. Both omit the governing amendment at top two. The acronym itself is absent from indexed text, but the deeper failure is status/version selection. Improving only lexical expansion for “SLA” may still leave the wrong version first. A later metadata/freshness gate and multi-evidence context must be evaluated separately.

The literal segment-ID probe asks for `D6:row-2:0`. That ID is metadata and **not** in either title/body search representation. BM25 returns no candidates; dense produces plausible runbook segments that do not match the ID. This is an exact lookup problem. The correct operational response is an authorized ID route or indexed identifier field, not a cosine threshold tuned on one query. Conversely, the Atlas `Sev-1` query contains a literal code also present in text, so both methods retrieve its agreement. Codes and opaque IDs therefore need separate slices.

The two numeric-constraint questions split evenly: both routes find the one-hour dated amendment but miss the Basic eight-hour agreement at top two, favoring other Sev-1 passages. Dense proximity can blur entities and quantities; BM25 can overweight repeated shared terms. A matching number alone does not prove the product, status or date. The two negation questions happen to work at top two in this fixture, yet a positive result from two examples does not establish that either model reliably handles “not signed” or “not contractual.” Add contradicted and near-duplicate cases before asserting a general ability.

The Spanish-to-English probes both hit their targets at top two in this fixture, partly because names and `Sev-1` survive translation; BM25 also succeeds. This does **not** validate cross-lingual transfer by the English-focused model. The query distribution is tiny, source passages are English, and no native assessor checked phrasing. A real language evaluation needs directions, native queries, qrels, scripts, entity variants and a multilingual-capable model. Chapter 12's distinction between multilingual monolingual and cross-lingual retrieval still applies.

For `none-orion` and `none-private`, both systems return top-*k* candidates despite zero eligible positive evidence. Exact dense search fills the heap whenever eligible vectors exist; a high rank means only *highest among the eligible set*. A similarity threshold can reject low scores only after calibration on representative positives and negatives for this exact encoder, corpus, scope and query distribution. The two no-evidence examples do not calibrate one. Retriever confidence and answer confidence are different; context selection and a generator must later test answerability and abstention. D10 remains outside the support-team scores even when the query explicitly names it.

Failures should be localized with an ordered checklist: verify source/segment exists and is eligible; verify version and searchable text; inspect query/document encoding contract and truncation; inspect raw scores and rank before context; compare BM25; check whether the correct candidate is at larger `k`; only then consider changes to representation, routing, filters or the answer path. A missing target at `k=2` but present at `k=8` is a ranking-depth problem, while absence from the corpus or scope is an ingestion/eligibility problem. Do not relabel a restricted passage as “irrelevant” to make recall look better.

## 6. What this stage unlocks

The V3 artifact is a complete *exact dense candidate generator* with a reproducible index contract, batch build measurement, warm query trace, judged failure slices and a frozen in-memory parity oracle. It is still one CPU process over 13 short segments. Chapter 14 will contrast single-vector retrieval with learned sparse and late-interaction representations; Chapter 15 will introduce approximate search only after this exact baseline. Hybrid routing comes later because its gain must be measured against these lexical and dense failures. Vector databases and services are implementation choices after the scoring, eligibility, version and evaluation contracts are understood.
