## 1. A coarse index is an inverted file of vectors

In Chapter 5 an inverted index maps a term to the documents containing it. An **inverted file for vectors (IVF)** maps a learned coarse-cell ID to the IDs of vectors assigned to that cell. The analogy is organizational, not semantic: cell membership means *nearest trained centroid under a chosen metric*, not shared words or relevance. A centroid is a representative coordinate vector. Set `nlist` to the number of centroids and `nprobe` to the number of nearby centroid lists inspected for a query. The [Faiss index documentation](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes) describes this cell-probe family and distinguishes IVF with full vectors from IVF with compressed codes; our program implements the data movement independently.

To train a simple coarse quantizer, sample representative passage vectors and run a clustering procedure such as k-means. Our Lloyd-style teaching implementation seeds centers by farthest-first selection, assigns each training vector to its nearest center, and replaces each center by the mean of its group for eight iterations. **Training is index-time work.** It has no question labels and does not teach the retriever which passages answer a question. Then assign every indexed passage `x` to exactly one nearest centroid `c_j` and append its stable ID and payload to list `j`. A list may be much longer than another; `nprobe/nlist` is therefore only a rough intuition for the fraction of vectors read. Measure actual list occupancy and eligible scored count.

At query time, encode and normalize `q` under the **same model and metric contract**, compare it with all `nlist` centroids, choose the nearest `nprobe` cells, gate the IDs by trusted eligibility, score their vectors and select top-*k*. **IVF-Flat** keeps original full vectors in the lists. Its scores inside probed lists are exact, but the *candidate set* can be incomplete. If `nprobe=nlist`, every eligible full vector is scored and IVF-Flat must agree with the exact oracle, provided there is no separate scan cap, stale row, metric mismatch or tie-rule difference. That setting removes coarse-search approximation and usually forfeits its speed rationale. It does not turn a bad embedding into good evidence.

```text
INDEX TIME  frozen model + source snapshot → training sample → coarse centroids
            all eligible passage vectors → nearest centroid → list ID + stable passage ID + full vector

QUERY TIME  question → frozen query encoder → nearest nprobe centroids → their lists
            → eligibility gate → exact distance on retained vectors → candidate top-k
            → later context selection → later grounded answer
```

Consider the computed two-dimensional example in Figure 16.01. Sixteen unit-circle points form four trained lists. Query `q` at 38° has exact top-two IDs `01` and `02`. The nearest centroid's list contains `01` but not `02`, so `nprobe=1` returns `01,00`; probing the second cell restores `01,02`. This is a **coarse-list miss**: no within-list ranker can score `02` until its list is probed. The figure's cell borders depict nearest-centroid assignment in normalized two-dimensional space. They are not a proof about 384-dimensional language embeddings.

### The coarse cost is not just the vectors scored

With `N` passage vectors of dimension `d`, `C=nlist` centroids, `P=nprobe` probed lists and `S` eligible vectors in those lists, a straightforward query pays approximately `O(Cd + Sd + S log k)` for centroid comparison, exact vector distances and bounded top-*k* selection. Our transparent Python code materializes score pairs, so its object allocation adds costs outside that expression. Training and assigning rows cost much more than a query and must be amortized over traffic and index lifetime. The stored float32 vector payload alone is `4Nd` bytes; centroids add `4Cd`, IDs and list metadata add more. For a million 384-dimensional rows, raw float32 coordinates are about 1.43 GiB before IDs, replicas, source text and allocator overhead. An optimized batched full scan can still beat poorly tuned IVF at modest sizes or when `P≈C`.

Centroid placement matters. A training sample concentrated on one source, language, tenant, time period or embedding version can leave other populations in overloaded or poorly placed cells. New inserts use the **old** centroids unless a rebuild is planned. Empty and unbalanced lists change latency and recall. Increasing `nlist` may reduce average list length but adds centroid work and requires enough representative training vectors. Increasing `nprobe` raises candidate coverage and work without changing stored bytes. The [Faiss maintainers' FAQ](https://github.com/facebookresearch/faiss/wiki/FAQ) explicitly recommends setting `nprobe` to all lists when diagnosing whether an accuracy loss comes from coarse probing; that is an *experiment*, not a production tuning rule.

## 2. Compression changes distances even after all lists are probed

**Quantization** replaces a continuous coordinate or vector region with one of a finite set of representable values. A basic **scalar quantizer** rounds each coordinate separately. If values are clipped to `[-1,1]` and divided into 256 uniformly spaced levels, the spacing is `Δ=2/255≈0.00784`; nearest-level rounding incurs at most `Δ/2` absolute error *per unclipped coordinate*. Before renormalization, a `d`-coordinate vector's Euclidean reconstruction error is at most `√d·Δ/2` under this specific bounded input assumption. Out-of-range clipping, a different fitted range, metric transformation and normalization change the bound and ranking behavior. Scalar quantization shrinks float32's four bytes/coordinate to roughly one byte/coordinate at eight bits, plus scale and offset metadata. It does not exploit relationships among coordinates.

**Product quantization (PQ)** groups a `d`-coordinate vector into `M` equal-width subspaces, learns a small **codebook** of `2^b` representative subvectors per subspace, and stores only the `b`-bit index of the nearest codeword in each group. The payload is `M·b` bits per vector, rounded and packed to bytes, plus IDs, codebooks and any coarse index. For `d=32`, `M=8`, `b=2`, eight two-bit indices need **16 bits, or two packed bytes**, rather than 128 raw float32 coordinate bytes. Four codewords per subspace are severely limited; the byte reduction alone says nothing about recall. Larger `b` improves representational capacity but enlarges codebooks and lookup work. Different subspace partitions or a learned rotation can change distortion; our code uses contiguous subspaces and no rotation. Read [Jégou, Douze and Schmid's original PQ paper](https://doi.org/10.1109/TPAMI.2010.57) for the broader method, not as a performance promise for this toy.

In **residual IVF-PQ**, each passage `x` is first assigned to coarse centroid `c_j`; PQ encodes the residual `r=x−c_j`, not the complete vector. This makes the coarse representative and short residual code a two-stage reconstruction `x̂=c_j+ĉode(r)`. We train residual codebooks from the same training sample after assignment. The training sample needs enough members and coverage for both centroid and codebook learning. A tiny training set can fit the indexed points poorly; our V0 twelve-row example is deliberately inadequate for a production 384-dimensional, eight-subspace codebook.

Figure 16.01's right-hand arithmetic is fully checkable. Let `x=(1.4,1.7)` and its centroid `c=(1,0)`, so `r=(.4,1.7)`. Give the first one-coordinate subspace codebook `[0,.5]` and the second `[0,2]`. The nearest codeword indices are `(1,1)` and reconstruct `x̂=(1.5,2)`. The squared reconstruction error is `(.1)²+(.3)²=.10`. For query `q=(1.2,1.8)`, exact squared distance to `x` is `(.2)²+(.1)²=.05`, while reconstructed squared distance is `(.3)²+(.2)²=.13`. A competing vector with true squared distance between those numbers can reverse order under the approximation. This toy is unnormalized L2 arithmetic; the V4 experiment normalizes stored and query embeddings and then uses squared L2, which preserves the original cosine order **only for the original unit vectors**. A reconstructed PQ vector is generally not unit length, so treating its approximate L2 score as an exact cosine similarity would be wrong.

### Lookup-table distance and exact refinement

At query time, for each probed coarse list `j`, subtract `c_j` from query `q`. For subspace `m`, precompute a table of its squared distances to every codeword. A stored item's approximate squared distance is then a sum of `M` table entries:

`D_ADC(q,x) = Σₘ ||(q−c_j)ₘ − Bₘ[codeₘ(x)]||²`.

This is **asymmetric distance computation (ADC)**: the query remains full precision, while indexed residuals are quantized. We need a separate table for each probed centroid because `q−c_j` changes. The lookup construction costs roughly `O(P·2^b·d)` coordinate operations; scanning `S` codes costs roughly `O(SM)` table additions, plus selection. Actual SIMD layout, code packing, cache behavior and memory bandwidth determine optimized performance. The [Faiss index guide](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes) calls the residual IVF-PQ combination `IndexIVFPQ`; our implementation uses ordinary Python tuples and is an explanation, not a speed comparison with Faiss.

An optional **exact refinement** retains original vectors somewhere, selects the top `R≥k` ADC candidates, and recomputes their original distances before returning top-*k*. This can correct a PQ rank reversal **only if the true neighbor survived the probed-list and ADC top-`R` gates**. It cannot restore a point in an unprobed list or one pushed below `R` by quantization. Retaining originals also gives back much of the vector-storage cost; fetching them from a separate store adds I/O, latency, version and authorization obligations. State whether quoted bytes include those originals.

```text
INDEX TIME  sample → coarse k-means → assign each x to one list
            sample residuals (x−centroid) → M subspace codebooks
            each indexed residual → M short codeword IDs + passage ID + scope/version

QUERY TIME  q → nearest P centroids → allowed IDs in probed lists
            → per-list ADC lookup tables → approximate top-R
            → optional original-vector fetch and exact top-k refinement
            → candidate IDs/scores → later evidence and answer stages
```

### Decompose the error before tuning

Compare four results on the **same vectors, metric, scope, source snapshot and query**:

1. Exact full scan is the geometric oracle.
2. IVF-Flat at chosen `nprobe` exposes coarse-list loss only.
3. IVF-PQ ADC at the same `nprobe` adds compression and approximate-score loss.
4. ADC top-`R` followed by exact refinement tests how much of that score loss remains after a bounded shortlist.

The list-coverage fraction is `|oracle top-k IDs whose lists were probed|/k`. Under the same exact metric and deterministic tie rule, **IVF-Flat top-*k* recall equals this fraction**: every probed member of the global top-*k* must also rank in the probed set's top-*k*, while an unprobed ID cannot appear. When all lists are probed, coverage is one. If IVF-Flat then disagrees with exact, investigate implementation, metric, update or scope—not quantization. With all lists probed, any ADC-versus-Flat disagreement isolates compressed-distance ranking error. Exact-neighbor recall still measures geometry, not human relevance. Keep judged qrel recall, context IDs and future answer measures separate.

## 3. A measured V4 comparison

The [checked V4 record](../projects/V4/chapter-16-experiment.json) freezes the code hashes, seeds, data versions, procedure and per-query candidate IDs. Its controlled synthetic workloads contain Gaussian unit vectors and 16 planted noisy queries each: `(N=256,d=8,nlist=8,M=4)` and `(N=1024,d=32,nlist=16,M=8)`, both with two bits per subspace. Up to 256 indexed vectors are sampled without replacement for training. Each query tests `nprobe∈{1,2,4,all}` under the same centroids/codebooks, with IVF-Flat, PQ ADC and top-eight exact refinement. Two randomized-order warm timing passes follow a warm call per method/query. There are no human qrels in this workload; its quality measure is exact-neighbor Recall@2. These are local Python search times, not service tails.

| `N=1024,d=32` | Oracle IDs in probed lists | Exact-neighbor Recall@2 | Eligible scored mean | Search-only p50 ms |
|---|---:|---:|---:|---:|
| Exact full scan | 1.000 | 1.000 | 1024 | 2.821 |
| IVF-Flat, `nprobe=1` | .313 | .313 | 64.94 | .355 |
| PQ ADC, `nprobe=1` | .313 | .063 | 64.94 | .202 |
| ADC top-eight + exact, `nprobe=1` | .313 | .188 | 64.94 | .256 |
| IVF-Flat, `nprobe=16` | 1.000 | 1.000 | 1024 | 4.834 |
| PQ ADC, `nprobe=16` | 1.000 | .125 | 1024 | 1.920 |
| ADC top-eight + exact, `nprobe=16` | 1.000 | .375 | 1024 | 1.842 |

The result is informative precisely because it is unfavorable to a simple “compressed means better” story. At one probe, most oracle neighbors are never in the candidate lists. At all probes, IVF-Flat recovers every exact ordered top two, while this tiny-codebook PQ version still loses most geometric neighbors. Its mean squared reconstruction error on indexed unit vectors is `.565`; that distortion is diagnostic, not itself a recall metric. Top-eight refinement helps, but many true neighbors rank below eight under the approximate score. Full-probe IVF-Flat is slower than this Python exact scan because it scans the same 1,024 vectors **plus** centroid and list overhead. PQ's measured Python speed at all probes is paired with poor recall; it is not an acceptable substitute merely because its p50 is smaller.

For the same 1,024-by-32 case, theoretical float32/index payload lower bounds are **138.0 KiB** for IVF-Flat, **12.5 KiB** for packed PQ without originals, and **140.5 KiB** for PQ with originals retained for refinement. Those figures include eight-byte numeric IDs, 16 coarse centroids and the small codebooks; they exclude Python objects, list offsets, scopes, allocator overhead, replicas and source text. The code actually stores Python tuples, so these are **not measured resident bytes**. The compressed-only path cannot run exact refinement without another original-vector store. The 256-by-8 case shows the same qualitative separation: one-probe IVF-Flat recall `.406`, PQ ADC `.250`, refinement `.406`; full-probe Flat `1.000`, ADC `.375`, refinement `.813`. Its different dimensions and training set do not establish a scaling law.

### The judged twelve-vector regression says something different

The V0 diagnostic reuses Chapter 13's 14 inspected questions and complete 168 judged query-passage pairs for the twelve eligible `support-team` vectors. It trains three coarse cells and eight two-bit residual subspace codebooks on those same twelve vectors. That is enough for a teaching trace and far too little to claim a robust 384-dimensional codebook. The legal-only D10 vector is excluded **before** this static index is trained or searched. The pinned query encoder takes about `10.14 ms` median in this run; exact scan takes `.405 ms` median search-only. With `nprobe=1`, IVF-Flat scores 6.57 eligible rows/query on average and has geometric Recall@2 `.857`, but its judged macro positive-query Recall@2 falls from the exact route's `.792` to `.708`. With all three lists probed, Flat returns exactly the oracle top two and restores `.792` judged recall. PQ ADC with all lists has only `.500` geometric recall yet the *same* `.792` aggregate judged recall; top-four refinement has `.714` geometric recall and `.875` aggregate judged recall. The latter apparent judged gain is a small, inspected-set ranking accident, not evidence that this PQ codebook improves retrieval. All-list Flat takes `.923 ms` and ADC `1.139 ms` median search-only on this Python implementation, both above the `.405 ms` scan; query encoding dominates all three.

Inspect `spanish-fee`: its exact top two are `D6:row-2:0` and `D1:§8:0`. One-probe Flat returns two D4 steps and its oracle-list coverage is zero: this is a coarse miss. All-list PQ ADC returns `D4:step-4:0` and `D7:timeline:0` despite both oracle IDs now being available: this is compressed-score loss. All-list top-four refinement restores the exact pair because both survived the ADC shortlist. In `code-segment`, the all-list top-four refinement still fails to restore the full exact pair; a true neighbor fell below the shortlist. Meanwhile `acronym-sla` remains a Chapter 13 representation/source-status issue when even exact dense retrieval misses the current signed clause. No index geometry fixes an exact-oracle failure. The two no-evidence questions have no eligible positive qrels; an empty or changed candidate list is not proven abstention.

## 4. Index lifecycle, policy and debugging

Index training, vector assignment, code generation and query probing must share a versioned embedding contract. An embedding-model change invalidates centroid geometry and residual codebooks even if dimension stays 384. A source update can change a passage's vector and cell; treat it as a versioned replacement, not an in-place code tweak. Inserts can be assigned with existing centroids/codebooks, but their distribution may drift. Deletes need a tombstone or removal from lists **and** from raw-vector/refinement stores and caches; compacting lists and retraining eventually remove dead IDs. The teaching code exposes insert and tombstone behavior but does not implement durable persistence, atomic alias swaps or deletion propagation. Chapter 22 treats freshness; Chapters 50–51 take on production migration and distributed ownership.

A trusted policy gate must run before scoring and context selection. Our V0 index is built from a static already eligible support-team roster, and the query checks that scope again; this is not live authentication. Training shared centroids on restricted vectors can itself create a sensitive derived artifact, even if query results filter IDs. Multi-tenant designs need a policy for training data, list sharing, authorization updates and tenant-safe caches. Source licensing and retention apply to vectors, centroids/codebooks learned from them, raw refinement copies, logs and backups. Do not log raw private questions or tenant IDs as metric labels. Record protected request/trace IDs, source/index/model/codebook versions, `nlist/nprobe/M/b`, probed list IDs and lengths, eligible/scored count, approximate top-`R` IDs/scores, refined IDs/scores, empty-list reasons, build/encoding/search/refinement durations and snapshot age in restricted traces. Aggregate bounded labels for list imbalance, ANN oracle recall, judged recall, latency, build/refresh cost, bytes and tombstone lag. A score from a PQ reconstruction is not a calibrated relevance or answer-confidence value.

When quality falls, inspect in this order: (1) is the current eligible passage present in the source and index? (2) does the exact oracle retrieve it? (3) does its centroid list get probed? (4) does ADC put it in top `R`? (5) does exact refinement retain it in top-*k*? (6) does context select the relevant span? (7) does the generator cite and use it correctly? Increase `nprobe` to all lists **as a diagnostic** for coarse loss. Compare all-list ADC with all-list Flat for compression loss. Raise `R` for shortlist loss, then check whether original-vector fetch erases the latency/memory advantage. If exact itself misses the passage, return to model, metadata, chunk, lexical or source-quality analysis. In all cases, rerun frozen qrels and inspect failures; a high aggregate geometric recall cannot authorize a deployment.

Our V4 decision remains to keep exact dense search as the candidate oracle. The experiment is a controlled mechanism demonstration, not a production benchmark. A real replacement needs representative independently judged questions, filtered and multilingual slices, multiple training samples/seeds, corpus-size and update mixes, actual resident bytes including originals/replicas, build and refresh cost, warmed and cold stage/end-to-end p50/p95, and a predeclared relevance and latency gate. Chapter 17 will ask whether a navigable proximity graph offers a better frontier; it inherits the same exact oracle and eligibility discipline.
